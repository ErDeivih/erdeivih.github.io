Fondo Popular

Turn the federation portals into a queryable database of federated football in Castile and León.

Fondo Popular (internal and repository name, FACyLF) brings federated football in Castile and León, futsal included, into a canonical database and publishes a web front end to explore it: standings, fixtures, results, line-ups, top scorers and player histories.

What it is, what it is for and what I built

What it is. A canonical database of federated football and futsal in Castile and León, with a web front end to query it: standings, fixtures, match reports, top scorers and player histories.

What it is for. To answer questions that today take dozens of federation portals: how many matches have a report, which teams have played at national level or how a table has changed.

What I built. Collection with Selenium and a resumable SQLite queue, the idempotent PostgreSQL importer, the core, analytics, source and ops schemas, the aggregate projection and the web front end. Also the publishing step with a check: the published database is compared table by table with the canonical one.

Decision I can point to: The collector stores every page in a SQLite queue before parsing, and the importer uses natural keys: if it stops halfway, it can be resumed without duplicating rows.

What I did not do. The data is not mine: the federation publishes it. I do not include club crests without permission and the full application is not public; what is published is a static demo with real data.

The problem

Fixtures, matchdays, standings and match reports live on federation HTML portals, with one page per season, and club and team names change between sources. Without a canonical database, a question such as “how many 2014-15 matches have a match report?” means opening dozens of tabs and cannot be verified.

Approach

  • Collects the portals with Selenium and headless Chrome, using a per-federation SQLite queue (jobs, reports and requests) that retries and resumes.
  • Imports into PostgreSQL with an idempotent importer: an interruption neither loses work nor duplicates data.
  • Publishes behind two reconciliation gates: the published database must match the canonical one.
  • Serves a web app with search, a province selector, competitions, standings, match reports, player history and rankings.
  • Runs a daily scheduled task; on the happy path it prints a single coverage line.

Data and data model

The model separates schemas, which is the part closest to a real Data Mart:

Schema Content
core canonical model: competitions, groups, matches, match reports, clubs, team-seasons and registrations
analytics aggregates: standings, rankings and player histories
source evidence of the source ingestion
app and ops users and operations
  • Separate entities for club, team-season and registration, so an entity is not confused with its participation in a competition.
  • Every record keeps provenance and timestamps; versioned migrations and read-only roles.
  • Current volume: 15 seasons (2012-13 to 2026-27), 867 competitions, 3,961 groups, 328,100 matches and 312,897 match reports.
  • Coverage KPI: an edition is “complete” when all its groups have the corresponding checkpoint. 206 of 867 are complete (23.8%); the per-season table is published and updates itself.
  • Quality: the encoding checker catches double encoding and invalid UTF-8 (0 problems in Castile and León); idempotency is shown with before/after counts; the last publication reconciled 98/98 tables and 123,601,068 identical rows.

What I learned building it

  • Data models and Data Marts: separate schemas and entities that distinguish a club from its registration in a competition.
  • ETL: collection, a resumable queue, idempotent import and publication with reconciliation.
  • KPIs: a single definition of “complete edition” and coverage measured per season and group rather than guessed.
  • Data quality: encoding checker, query budgets and contract tests against the canonical database.

Real state

Done and verifiable: a static demo published with real 2026-27 data, the full app on a private server with every season, and a daily scheduled pipeline.

Pending: 178 editions cannot be recovered from the current sources and the rest are still being collected; data-quality dashboards for operations and a real usage metric are still missing.

The FACyLF name remains in the repository and the code; publicly, the product is called Fondo Popular.
